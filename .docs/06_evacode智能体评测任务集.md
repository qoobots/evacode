## 1. 判定方法：为什么用"提交自带的新增测试"

本仓库的近期提交有个极有价值的特征：**修一个 bug 的同时往往顺手补了测试**。
例如 `93a4da42` 改 2 个文件，其中一个是 `protocolServerHandler.test.ts`（+148 行）。

这让我们可以直接套用 SWE-bench 的判定方式，而不用人工写验收标准：

| 概念 | 含义 | 在本仓库怎么取 |
|---|---|---|
| **FAIL_TO_PASS** | 任务原本失败、做对后应通过 | 该提交**新增/修改**的测试 |
| **PASS_TO_PASS** | 做任务时不能弄坏 | 同一测试文件里其它既有测试 |
| **判定命令** | 可自动执行 | `npm run test-node -- --grep <测试名>` 或针对该文件的既有测试入口 |

**做法**：把某个提交的代码改动回滚、**保留它的测试改动**，让智能体从零重做代码部分。
跑测试即可判定，无需人看代码。

> ⚠️ 前提是这些测试入口在本机能跑通。**尚未实测**——这是 0.7（最小 runner）要验证的第一件事。
> 若 `test-node` 入口不可用，退化为「人工打分 + 双跑对照」的最小版本（见 §4）。

## 3. 指标与对照

| 指标 | 怎么取 |
|---|---|
| ① 完成率 | FAIL_TO_PASS 全部通过记为完成 |
| ② token 消耗 | 由 `eva-ai.trace` 的真实 `prompt_tokens` 汇总（EVA 网关会回传） |
| ③ 工具轮次 | 主循环里 `sendRequest` 的次数 |
| ④ 人工介入次数 | 跑任务过程中人不得不干预的次数（权限确认不算） |
| ⑤ 首改延迟 | 从提交请求到产生第一个正确编辑的时间 |

**四家对照**（Q7 保留三家，正好是天然对照组）：同一任务集分别跑
`Copilot` / `Claude` / `Codex` / `eva-agent`，出对比表。

> 对照要注意的可比性：三家的模型、工具集、权限默认值都不同。
> 前几轮先只把它们当作"参考区间"，不要直接下"谁更好"的结论，等 runner 稳定后再谈可比性。
